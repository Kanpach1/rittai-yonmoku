# 立体四目 要件定義(ドラフト v0.5)

## 1. 目的

自分が一番楽しめる立体四目を作る。柱は2本。

1. **最強のAI**: 既存最強AI([mikanakim/score4_AI](https://github.com/mikanakim/score4_AI)、以下「既存最強AI」)を超え、最終的には完全解析にもとづく「負けないAI」にする。
2. **気持ちいい手触り**: iPhone / iPad で、玉を落とす感触・音・振動・演出が気持ちいいこと。

### スコープ外(今は作らない)

- オンライン対戦、マッチング、ランキング
- 初心者向けのチュートリアルや、続けたくなる仕組み(戦績・実績など)
- App Store での一般公開(自分の端末に入れるだけ)

## 2. 想定環境

| 項目 | 要件 |
|---|---|
| 主な端末 | iPhone(縦持ち)、iPad(縦・横の両方) |
| 実行形態 | Capacitor で包んだ iOS アプリを自分の端末に入れる。中身は今と同じ Web(`index.html`)なので、ブラウザでも遊べる状態は保つ |
| 開発・ベンチマーク | 手元の Mac でネイティブ実行。Intel Core i7-8569U(4コア8スレッド)、メモリ16GB、空き約170GB |
| 完全解析の本番 | クラウド(→ 6章) |

## 3. 機能要件

### 3.1 AI・エンジン

- **E-1 ベンチマーク基盤**: 既存最強AI と自動で連続対局して勝率を出せる。探索速度(ノード/秒)と、決まった局面集での正解率も測れる。
- **E-2 高速化**: 盤面をビットボード(64マス=64ビット)で持つ。対称形をまとめた置換表、手の並べ方の改善、決勝点(重力つきの「次に置ける場所」)の扱いを強くする。
- **E-3 並列化**: Mac では全コア、ブラウザでは複数の Web Worker で探索する。
- **E-4 完全解析**: 初期局面が先手必勝・後手必勝・引き分けのどれかを証明する。結果は他の手段で検証できる形(証明木やデータベース)で残す。
- **E-5 完全解析AI**: 解析結果を対局に使い、「最強」より上の「完全」レベルを作る。アプリに入れるデータの大きさは要検討(サーバーを置かない前提)。
- **E-6 研究用の表示**(任意): 各手の評価値、読み筋、「この手で勝ち/負けが確定」を盤上に出せる。

### 3.2 手触り・演出

- **U-1 操作**: 棒に触れたら即座に反応する。
  - 触れる: 棒を選び、次に玉が止まる位置にゴースト玉で予告する。棒の選び方は先端を最優先にする(→ design.md)
  - 離す: 選んだ棒に玉を落として確定する(押し間違いは「待った」で戻す)
  - 押した位置から一定距離(初期値10px)以上動かしたら盤の回転に切り替え、その操作では着手しない。時間では判定しない
- **U-2 落下**: 玉が棒を滑り落ち、着地でわずかに沈み込み、戻って静止する。跳ねない。重さが感じられる動き。
- **U-3 音**: 着地音は段と玉の重なりで変わる。リーチ・勝ちには専用の音を付ける。
- **U-4 振動**: iOS の触覚フィードバック(Capacitor の Haptics)を使う。着地・リーチ・勝ちで強さと質感を変える。ブラウザで動くときは振動なしで、音と動きだけにする。
- **U-5 勝ちの演出**: 揃った4つが光って線で結ばれる。視点が自動でその線が見える向きに回る。
- **U-6 見やすさ**: 立体で隠れた玉やリーチを見落とさない(半透明、リーチの印など)。通常環境では盤面は3D表示のみを使用する。見取り図・平面図への手動切替UIは提供しない。
  - 3D表示が利用できない環境では、プレイ継続手段として平面表示を使用してよい。この平面表示は通常UIの機能ではなく、互換性のためのフォールバックとして扱う。
- **U-7 iPad 横画面**: 盤を大きく出し、横に棋譜・評価を並べるレイアウト。
- **U-8 滑らかさ**: 常に 60fps。AI が考えている間も画面が止まらない。

### 3.3 今あるもの(維持)

AI の段階選び、二人対局(1台)、待った、振り返り、棋譜のコピーと読み込み。

## 4. 非機能要件

- **エンジンは C++ で書く**。同じソースを、Mac ではネイティブで、アプリとブラウザでは Emscripten で WebAssembly にして動かす。
  - アプリ内でネイティブ C++ を直接呼ぶ(WebAssembly より速く、マルチスレッドも楽)のは、必要になったら検討する。
- ビルドは必要になるが、Web の成果物は今と同じく「`index.html` 1ファイルを開けば遊べる」形にする(WebAssembly を HTML に埋め込む)。
- エンジンにはテストを付け、速くしても結果が変わらないことを毎回確かめる。
- オフラインで動き、サーバーを持たない。
- **長時間の解析は止まっても続きから再開できる**こと(途中結果を定期的にディスクに保存する)。

## 5. 判定基準

### 5.1 「既存最強AI を超えた」

次をすべて満たしたら「超えた」とする。

- **条件をそろえる**: 同じ Mac で、どちらも1スレッド、1手あたり同じ思考時間。思考時間は **1秒** と **5秒** の2通り。
- **序盤のばらつき**: 初手から数手の合法な開始局面を50個用意し、それぞれ先後を入れ替えて **計100局** 指す(同じ対局の繰り返しを防ぐため)。
- **合格ライン**: 勝ち=1点、引き分け=0.5点で、**得点率60%以上**(100局なら、偶然でこれを超える確率は数%以下)。これを両方の思考時間で達成する。
- **参考値**(合否には使わない): 探索速度(ノード/秒)と、同じ局面を解き切るまでの時間を 既存最強AI と比べて記録する。

### 5.2 完全解析

- 初期局面の結果(先手必勝・後手必勝・引き分け)が出ていて、証明データを使った別プログラムで検算できる。

## 6. 計算環境

**手元の Mac で数時間〜一晩程度までは回してよい。何日も連続で回す解析はクラウドに移す。**

手元の Mac のバッテリーは既に劣化している(充放電813回、macOS の判定は「修理サービス推奨」)。全コアで何日も回すと、熱と電源つなぎっぱなしの負荷でさらに傷み、膨張の危険もある。

| 用途 | 場所 | 目安 |
|---|---|---|
| 開発・テスト | 手元の Mac | 制限なし |
| ベンチマーク(5.1 の100局など) | 手元の Mac | 1回 数十分〜数時間。スレッド数を絞り、終わったら止める |
| 解析時間の見積もり | 手元の Mac | 小さめの問題(終盤の局面、数手進めた局面)を解く時間を測り、全体を見積もる |
| 完全解析の本番 | 一晩で終わる見込みなら手元の Mac、それ以上ならクラウド(多コア・大容量メモリのマシンを時間課金で借りる) | 見積もりを見てから決める |

- 解析プログラムは、止まっても途中から再開できる作りにする(非機能要件)。これでクラウドの安い「中断されうる」マシンも使える。
- 手元で長めに回すときは `caffeinate` でスリープを止め、スレッド数を4以下に絞り、風通しのいい場所に置く。数時間ごとに区切って休ませる。
- トラックパッドが浮く、筐体にすき間ができるなどの膨張の兆候があれば、使うのをやめる。

## 7. 未決事項

2. **アプリへの入れ方**: 無料の Apple ID でも自分の iPhone に入れられるが、7日ごとに入れ直しが必要。Apple Developer Program(年額 99ドル)なら1年有効。どちらにするか。

### 先行研究(2026-10-08 調査)

- **重力つき 4×4×4(立体四目、Score Four、Connect-Four 3D)は未解決**とされている。2026年春の Harvard の講義ノート([arXiv:2605.20243](https://arxiv.org/abs/2605.20243))の表で「Open: Connect-Four 3D on 4³ unsolved」とされ、出典は『Winning Ways』。
  - 同じノートの本文に「4×4×4 Connect-Four 3D は 1988年10月に Allen と Allis が独立に解いた」と読める文があるが、これは文の崩れで、1988年に Allen と Allis が解いたのは通常の 7×6 の Connect Four(先手必勝)。v0.1 で「解かれたとする資料がある」と書いたのはこの文の読み違いだった。
- **重力なしの 4×4×4(Qubic)は先手必勝**。Patashnik(1980)が証明し、Allis も1990年代に証明数探索(proof-number search)で解いている。重力つきの解析でも参考になる。
- **既存最強AI** は αβ 探索 + 定石で「世界最強」をうたうが、完全解析やベンチマークの記載はない。
- 調べた範囲は英語の主要な資料と日本語の検索結果まで。日本の愛好家による非公開の解析などがある可能性は残る。

**→ 完全解析ができれば、知られている範囲では初めての結果になる。** 手法は、証明数探索(PN / df-pn)と、αβ探索 + 置換表 + 対称性の組み合わせを候補にする。

## 9. 開発環境(段階0で用意したもの)

| ツール | 入れ方 | 備考 |
|---|---|---|
| clang++(Apple clang 17) | Xcode に付属 | Mac ネイティブ版のビルド |
| CMake 4.4 | `brew install cmake` | このMac(Intel)は Homebrew のビルド済み版がなく、ソースからビルドされる |
| Emscripten | `third_party/emsdk` に emsdk で導入 | Homebrew 版は LLVM をソースからビルドすることになり何時間もかかるため使わない。使う前に `source third_party/emsdk/emsdk_env.sh` |
| 既存最強AI | `third_party/baseline_ai` に clone して `make` | ベンチマークの対戦相手 |

`third_party/` は git の管理対象外。別のマシンで用意し直すときは次のとおり。

```sh
git clone https://github.com/emscripten-core/emsdk.git third_party/emsdk
third_party/emsdk/emsdk install latest && third_party/emsdk/emsdk activate latest
git clone https://github.com/mikanakim/score4_AI.git third_party/baseline_ai
make -C third_party/baseline_ai/score4
```
